# Contributing to Hourline

Thanks for helping make Hourline better! Bug reports, ideas, translations and code are all welcome.

## Ways to help

- **Try the beta** and tell us what breaks. Joining takes two minutes at
  [hourline.adevtutorials.in/#beta](https://hourline.adevtutorials.in/#beta).
- **Report a bug** in [Issues](https://github.com/Abbasa5251/hourline/issues). Please include:
  - your phone model and Android version
  - the app version (Play Store page, or `version` in `app.json`)
  - the cities and the date/time involved
  - what you expected and what you saw
  - a screenshot, if you can

  Time zone bugs are much easier to fix with the exact city, date and time.
- **Suggest a feature** in Issues before writing a large change, so we can agree on the approach first.
- **Send a pull request** for a fix or an agreed feature (see below).

## Getting set up

You need Node.js 22+, and Android Studio with an emulator, or an Android phone with USB debugging.

```bash
git clone https://github.com/<you>/hourline.git
cd hourline
npm install
npm run android                 # builds and installs the development build
npx expo start --dev-client     # later runs: just start Metro
```

Hourline uses native modules, so it needs a **development build**, not Expo Go. See the
[Expo docs](https://docs.expo.dev/develop/development-builds/introduction/).

## Making a change

1. **Fork** the repo and create a branch from `master`, e.g. `fix/sydney-dst-label` or `feat/widget`.
2. Make your change. Keep each PR to one topic.
3. Run the checks. All must pass:
   ```bash
   npx expo lint
   npx tsc --noEmit
   npm test
   ```
4. Try it on a device or emulator, in light and dark mode. Attach before/after screenshots for UI changes.
5. Open a **pull request into `master`**. Describe what changed, why, and how you tested it.

`master` is protected: every change goes through a pull request with one approving review, and direct pushes or
force-pushes are blocked.

## Project rules

These keep the app correct and the build reproducible. PRs that break them will be asked to change.

**Time zone accuracy (most important)**
- All time zone maths goes through [`src/lib/tz.ts`](src/lib/tz.ts).
- The rules are bundled (IANA tzdb via `@formatjs/intl-datetimeformat`, loaded in [`src/lib/intl.ts`](src/lib/intl.ts)).
  Never use the phone's own time zone data, `Date#getTimezoneOffset`, or raw `Intl` without the polyfill.
  This is how every phone gets the same answer.
- [`src/lib/tz-timeanddate.test.ts`](src/lib/tz-timeanddate.test.ts) checks the engine against timeanddate.com and
  **must keep passing**. When you update the time zone rules, update the fixtures in `src/lib/tad-fixtures.ts` from
  timeanddate.com, and document any intended differences in the test.
- Add a test for every time zone bug you fix, using the exact city, date and time.

**Expo and React Native**
- Add dependencies with `npx expo install <package>`, not `npm install`. It picks versions that match the Expo SDK.
- Use the [Expo docs for the SDK version in `package.json`](https://docs.expo.dev/versions/latest/). APIs change
  between SDKs.
- `android/` and `ios/` are generated by `expo prebuild` and are not committed. Change native behaviour through
  `app.json` or a config plugin in [`plugins/`](plugins).
- Screens live in `src/app/` (Expo Router). Components, hooks and helpers live outside it.
- Use `Pressable` from [`src/components/pressable.tsx`](src/components/pressable.tsx) for anything tappable. It adds
  haptic feedback.

**Style**
- TypeScript everywhere. Match the code around you: naming, comment density, colours from `src/theme.ts`.
- Every interactive element needs an accessibility label or role.
- Prefer small, focused changes and existing helpers over new dependencies.

**Privacy**
- Hourline collects no data. Don't add analytics, ads, trackers or network calls that send user data. If a feature
  truly needs the network, open an issue first.

AI coding assistants: [`AGENTS.md`](AGENTS.md) holds the same rules in a form tools like Claude Code and Cursor read
automatically.

## Commit messages

Use the imperative mood and a short summary line, e.g. `Fix Lord Howe half-hour DST label`. Add a body if the *why*
isn't obvious.

## Security

Please don't open a public issue for security problems. Email **hello@adevtutorials.in** instead.
